# CLIProxyAPI: обёртка для self-hosted деплоя

Разворачивает [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) на своём сервере: подписка Google превращается в обычный API-эндпоинт, закрытый твоим ключом. Гугловый API-ключ не нужен — авторизация идёт OAuth-логином аккаунта. Один контейнер, внешней базы нет.

## Как это работает

Ты один раз логинишься гугл-аккаунтом, токен ложится в `auths/` и дальше обновляется сам. Прокси держит эту сессию и отдаёт наружу OpenAI-, Gemini- и Claude-совместимые ручки. Агент ходит на них со своим ключом из `api-keys` — про Google он ничего не знает.

Доступ к моделям Google идёт через Antigravity, а не через Gemini CLI: в текущих версиях CLIProxyAPI гугловый вход только такой.

## Запуск

```bash
cp .env.example .env
cp config.example.yaml config.yaml
```

В `.env` укажи каталог с сертификатом, в `config.yaml` — ключи, которыми будут авторизоваться агенты. Дальше на сервер:

```bash
./sync.sh          # залить файлы и поднять контейнер
./sync.sh conf     # отправить .env и config.yaml
./sync.sh login    # OAuth-логин гугл-аккаунта
```

`login` запускает вход в контейнере на сервере и печатает ссылку. Открываешь её в своём браузере — колбэк вернётся по ssh-туннелю, который скрипт поднимает сам. После логина `./sync.sh restart`.

## Куда ходить агентам

На твой сервер, порт 228, ключом из `api-keys`. Больше клиенту знать нечего.

- OpenAI-совместимый API: `https://<ip>:228/v1`
- нативный Gemini: `https://<ip>:228/v1beta`
- Claude: `https://<ip>:228/v1/messages`

Для Hermes это запись в `providers:` с `type: openai`, `base_url: https://<ip>:228/v1` и твоим ключом.

## Что заполнить

`api-keys` в `config.yaml` — ключи для клиентов, список строк. Всё, что не с ними, прокси не пустит.

TLS поднимает само приложение, отдельного реверс-прокси нет. Каталог из `CERT_DIR` монтируется как `/certs`, пути к файлам прописаны в секции `tls`. Сертификата нет — ставь `enable: false`, но тогда ключ поедет по сети открытым текстом. Клиенты примут сертификат на IP, только если этот IP прописан в SAN.

`remote-management.secret-key` оставь пустым, если админский API не нужен: пустое значение выключает его целиком.

Остальные опции описаны в [config.example.yaml](https://github.com/router-for-me/CLIProxyAPI/blob/main/config.example.yaml) апстрима — можно добавить несколько аккаунтов и балансировать между ними.

## Как устроено

Контейнер один: готовый образ `eceasy/cli-proxy-api`, внутри слушает 8317, наружу отдан на 228. Состояние — три каталога рядом с compose-файлом: `auths/` с OAuth-токенами, `logs/` и сам `config.yaml`.

## Деплой

Хост и каталог задаются одной переменной в `.env`: `GPROXY_REMOTE=myserver:~/gemini-proxy-docker/`. Хост берётся из твоего `~/.ssh/config`.

`./sync.sh` заливает `docker-compose.yml`, примеры конфигов, README и сам себя, потом поднимает контейнер. Отдельные шаги: `code`, `conf`, `login`, `up`, `update` — подтянуть свежий образ, `restart`, `logs`.

Файлы с секретами едут только по `conf`. `auths/` не едет вообще: если один и тот же refresh-токен начнут обновлять два инстанса, они вышибут друг друга.

## Чего здесь нет

Бэкапов `auths/` нет. Потеряешь каталог — просто логинишься заново.

Файрвола нет: порт 228 открыт всем, доступ ограничивает только список `api-keys`.

Отдельная тема — риск для аккаунта. Google в 2026 году заявил, что усиливает выявление доступа к своим CLI-сервисам через сторонний софт, а это ровно то, чем занимается CLIProxyAPI. Прокси от этого не сломается, санкции прилетят аккаунту.
